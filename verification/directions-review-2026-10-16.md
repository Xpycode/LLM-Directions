# Directions review October 2026

Directions has earned its place as project memory, a source of tested platform knowledge, and a way to make completion claims checkable. Its weakest parts are competing instructions, repeated current-state records, and workflows that keep expanding before the user gets a useful result. The recommended change is a smaller mandatory core with procedures selected by the actual task, plus explicit stopping points for exploratory infrastructure.

This review covers August 16 through October 16, 2026. It incorporates three agent audits, additional project sampling, current source inspection, and primary web sources. It proposes changes; it does not authorize or apply a framework migration. The restart discussed in the earlier status exchange is outside this review.

**The most consequential collisions.**

1. **Old app-control instructions conflict with current consent, and tests can cross that boundary indirectly.** The logging command still tells the agent to quit test builds and relaunch the installed app. Your October 13 preference explicitly prohibits automatic app/desktop control without specific permission. The old cleanup step can also replace a fresh build intentionally left for testing. Current user instructions take precedence, but leaving both procedures active invites another mistake. Keep read-only process identification; make lifecycle changes conditional on current authorization, with full containing-folder paths for user-controlled handoff. [E11]

   There is also a recorded earlier violation: MousePlus's complete test scheme launched its app despite a request to continue without controlling it. Magpie's audit found updater tests that recursively cleaned the real Application Support directory; later work isolated them. No data loss is established by that record. Project test commands should disclose whether they are headless, app-hosted or interactive, which data namespace they use, and whether production startup is disabled. Reuse the isolation patterns already developed in ClipSmart and Magpie. [E23]

2. **Control infrastructure repeatedly delayed product evidence.** Directions records your surprise at only 2 of 25 tasks being complete and acknowledges that recovery infrastructure expanded without a usable pilot. The active task 1.3 now occupies 206 lines and 20,682 bytes. Penumbra later records the same concern about disproportionate control work; when you paused it and requested direct testing, an operator-driven playback check produced usable evidence. [E12, E13] Give each spike an observable result, an agreed work limit and a stop/replan condition. When it needs another subsystem, present the smallest usable alternative and the cost of continuing. Preserve unresolved safety evidence; a manual product test does not validate an unfinished automation mechanism. Recommend parking Mac-control development until its product value and scope are reconsidered.

3. **A documented deadline did not enforce the test boundary.** ClipSmart's log records a 30-minute isolated-profile smoke session still active more than 11 hours after launch. The deadline was not enforced, and restoration on the original Mac remained unconfirmed in the October 15 handoff. [E14] A long protocol is insufficient if its critical boundary has no reliable implementation. Prefer disposable app data that avoids swapping the daily profile. Where temporary state changes are necessary, explicitly agree the ending and recovery actions before starting and keep the obligation attached to its originating Mac. A timer does not grant permission to quit an app or restore a profile.

4. **Technical completion sometimes preceded agreement on a simple workflow.** MediaIngest records the user finding Workflow & Output overwhelming on September 17, then still overwhelmed on September 22, when the actual photo/video workflow was discussed and a replacement was planned. KinoBerlin reduced a 20-task statistics plan to seven tasks, then replaced consent-based browser collection with owner-selected passive server counting. [E15, E16] These records show rework and changing requirements; they do not establish that every earlier choice was unauthorized. Before a substantial UI or workflow implementation, demonstrate one representative user journey with concrete files, destinations and outcomes. Technical placement approval alone does not establish usability.

5. **Current state is mixed with superseded history.** The Directions state file records successful capture/reload and, farther down, a prepared capture that has not run. Its short Now section passes the current size heuristic while a 62-line Resume retains several superseded next actions. The same progression is repeated in the plan and task tracker. MediaIngest's September 17 daily log has 15 Next/Resume headings; CameraTranscoder's September 1 log has 19. Penumbra's October 10 log has 46 headings containing Resume in 1,386 lines; at inspection its state file fit 82 lines but contained 3,527 words. These are retrieval-burden measurements, not measured time loss; another active session continued updating Penumbra during the review. [E17, E24] Preserve chronological evidence, but maintain exactly one authoritative current handoff. Plan owns task completion and evidence; tracker owns backlog/inbox; state points to the current plan and next action. Historic records should not continue to present themselves as current.

6. **The generator can make a sync-conflict copy look authoritative.** A read-only preview during this review emitted both the canonical macOS guide and its September 8 Syncthing conflict copy. The generator admits numbered Markdown files and excludes redirect stubs, but does not sufficiently restrict canonical filenames. Ordinary Git status hides the conflict copy. [E18] Implement the already-planned eligibility check before another deployment. Preserve the conflict's content for reconciliation; exclude it from guidance generation.

7. **Copied and placeholder instructions still survive in consumers.** The website cohort found old universal mirrors in KinoBerlin, App-Websites, syncthingStatus, AppUpdater and VideoCorruptor. App-Websites and VideoCorruptor also retain generic documentation-folder agent instructions. App-Websites' nested template prescribes Swift checks and actor services for a website. [E19] This undercuts the shared-master design. Inventory exact duplicates and unique project additions before retiring copies. Keep project-specific knowledge and existing dirty work. This is instruction debt; a copied file's presence alone does not prove it caused an incident. Some consumer logs still report archive-blind checker warnings after the master fix; identify the actual invoked script/version before proposing another fix to the master. [E26]

8. **Generic guides compete with the command procedures.** The canonical execution command archives completed plans and their evidence. The context guide still prescribes deleting plans and maintaining a separate Resume file. The base guide tells the agent to run logging twice at session end and repeats obsolete lifecycle advice. [E20] Commands should own procedures. Conceptual guides should explain the reason and link to the procedure rather than restating it. The existing September cleanup plan needs to include the base guide as well as the context guide.

9. **User acceptance needs a finite remaining list and correct expectations.** Penumbra records the user asking how many tests remained; a three-check boundary was then set. Later acceptance instructions expected an export-queue row that the actual product intentionally filters out. Another instruction asserted the 120 fps zoom floor from pure-model tests without checking the integrated rate-provider fallback; a real provider defect was subsequently repaired. [E25] Before asking the user to test, verify the expected behavior against the integrated code and give one short batch with a stated end. Reconcile prior evidence first and say why any repeat is necessary. Contour's later evidence-reconciliation approach is a useful model. A failed real performance requirement, such as PlayPlayPlay's MXF headroom check, remains a legitimate gate.

10. **Build/test monitoring can manufacture false results or consume hours.** Magpie records a four-hour hang: parallel tests deadlocked, a pipeline exposed the wrong command's exit status, buffered output hid progress, and process matching found the MCP server instead of the owned build. A reported failure count also matched words in test names. [E27] Put the known safe command and serial-test requirement in the project's validation entry point. Preserve real exit status, track the owned process, retain progress logs and read structured results. Diagnose the harness before modifying working product code. This needs a small reliable command, not another orchestration framework.

11. **Published bytes and committed source can remain different after a successful release.** App-Websites' October 16 record explicitly says the focused Git snapshot retains older copy/CSS while publication receipts describe the deployed working-tree bytes. Preservation of unrelated work was correct, but this leaves reproducibility debt. [E26] Retain exact release manifests and arrange a scoped source checkpoint when authorized. Deployment permission does not itself grant permission to merge or push unrelated source. Cross-Mac lessons also include a KinoBerlin false remote-state claim after a failed directory change left the command in the local repository: verify repository identity before trusting a result. [E28]

**What the web adds.**

OpenAI's September guidance recommends narrow skill triggers, a small router with conditional references, and task-relevant document reads. It also warns that inherited test and approval instructions can overconstrain newer models. Apply that to duplicated scaffolding while preserving your explicit app-control boundary; vendor advice does not supersede it. [Rethinking skills and prompts](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra).

Anthropic recommends concise persistent instructions, keeping non-obvious project facts and using skills for occasional procedures. Its current guidance supports planning uncertain work while allowing small clear changes to proceed directly, and asks for checkable results. This fits the positive and negative project examples above. [Claude Code best practices](https://code.claude.com/docs/en/best-practices).

OpenAI's review guidance favors consequential, narrowly scoped invariants with a safe implementation path. Its skills evaluation guide recommends small checks of both outcomes and process, including unnecessary work. Use these principles to test Directions changes against representative tasks. [Custom review rules](https://developers.openai.com/blog/custom-code-review-rules-for-codex), [Testing skills with evaluations](https://developers.openai.com/blog/eval-skills).

Research does not support a blanket claim that instruction files always help or always hurt. The September revision of Gloaguen and colleagues' study reports no general task-success improvement and increased average inference cost in its settings. Lulla and colleagues report lower median runtime and output-token use over 124 pull requests from ten repositories. These are different evaluations, not measurements of Directions. The practical recommendation is a local comparison before expanding or deleting useful rules. [Gloaguen et al.](https://arxiv.org/abs/2602.11988v3), [Lulla et al.](https://arxiv.org/abs/2601.20404v2).

**Concise replacement instructions to consider.** These consolidate existing intent and the findings above; they are proposed wording, not installed policy.

> Choose process to match the task. Make a small, clear fix directly. For a new feature or uncertain workflow, agree the user-visible behavior and a proportionate plan before implementation.
>
> Load the instructions relevant to the action being taken. Keep durable local constraints in the agent entry point; link occasional procedures and technical references.
>
> Continue authorized ready work until it is complete or a real dependency, scope decision or explicit user limit requires a stop. Carry accepted decisions forward. Desktop and app control still require the user's specific permission.
>
> Validate the changed behavior. Reuse evidence while its source, artifact and relevant environment remain valid. Repeat broader checks when a change, failure or unresolved risk justifies them.
>
> Keep one current task status and one current handoff. Preserve historical evidence separately. Label unavailable checks and superseded decisions clearly.
>
> Before a spike grows another subsystem, compare the remaining work with the promised user outcome. At its agreed limit, present evidence and a concrete continue, simplify or stop decision.

**Recommended order.** Use the existing lean-efficiency plan as the home for overlapping work. A second optimization program would add another source of truth.

1. **Resolve correctness and authority first.** Fix the app-control collision, conflict-file eligibility and competing lifecycle instructions. Include the base guide in the existing cleanup scope. Reconcile the previous review's status: archive-aware index code is implemented and its live 61-file check passed during this review; the full planned fixture acceptance remains unproven.
2. **Reduce routine maintenance.** Establish one current state record, extract the conditional logging branches, retire the old installer and remove verified obsolete consumer copies in a small pilot. Add an early representative user journey and a bounded spike exit where those decisions matter. Preserve automatic handoff at genuine stopping points.
3. **Evaluate before broad rollout.** Try the revised workflow in Directions, one active macOS project and one website. Compare a small fix, substantial feature planning, approved continuation, blocked dependency, no-control build handoff, dirty cross-Mac arrival and session close. Record outcome, lost constraints, unnecessary questions, files read and repeated validations. Keep the current host/model stable for comparisons; source-byte reduction alone is not a speed result.

Keep hardware and release acceptance separate from implementation dependencies. For example, syncthingStatus's missing real notification-permission transition blocks a later UI wave in its current plan. Review whether those particular UI tasks truly depend on that evidence; do not change the user's notification settings or silently close the gate. [E29]

The current execution command already says to continue authorized ready work without renewed task/wave permission and avoid unnecessary broader reruns. Preserve those improvements and reconcile older contradictory advice. Separate wave requests in the logs do not prove the agent demanded unnecessary approval. Product requirements, migrations, releases, physical devices and app-control windows can legitimately need distinct decisions. [E22]
